# 笔录审查流程说明

## 图表文件

- `review-flow.drawio`：从上传、文档解析、6 域事实抽取到 34 条规则和前端处置的完整流程图。
- `review-sequence.drawio`：一次真实审查请求在前端、FastAPI、解析器、Qwen、规则引擎和存储之间的时序图。
- 两个同名 `.json` 文件是图表的结构化定义，方便后续修改节点和文字。

本机未安装 draw.io 桌面 CLI 和 Graphviz，因此本次交付经过 `.drawio` 结构校验，但未导出 PNG。两个 `.drawio` 文件均可直接用 draw.io 桌面版或 diagrams.net 打开编辑。

## 1. 文档解析与 QA

DOCX 通过 OpenXML 读取正文段落、表格、页眉、页脚和实际被引用的图片；PDF 根据页面是否有足够原生文本，选择保留原生文本或调用多模态模型识别。解析后的每个段落都带有来源类型、稳定 ID、页码和字符范围。

QA 重建不再按 Word 的单个段落机械切分。状态机从“问：”开始，持续收集跨段、跨页内容，直到下一个“问：”出现。完整的问、答以及答案中的图片转写共同形成一个 QA 证据块；不属于 QA 的原文保持为 text 证据块。

DOCX 图片现在记录其在正文块之间的位置。图片转写完成后先插回原位置，再执行 QA 重建，因此“答：见下图”后的图片属于当前 QA，不会统一落到全文末尾或最后一问。表格内图片按所在表格行之后插入。页眉、页脚图片继续使用兼容的尾部处理方式。

被害人信息不是文档的第二种分块。`victimProfile` 是从正文和表格的基本信息中单独派生的展示数据，必要时再用“基本信息”类 QA 兜底；证据主干仍然只有完整 QA 和非 QA text 两类。

## 2. 六个事实域

正常审查固定发起 6 个并发域请求：

1. `header_procedure`：笔录头部、程序告知和身份程序信息。
2. `case_timeline`：案件经过、时间地点、信息泄露和持续联系原因。
3. `contact_channels`：联系渠道、账号、切换和通话录音。
4. `online_money`：线上转账、损失、返款和逐笔转账实体。
5. `offline_delivery`：线下交付、取现和对应逐次实体。
6. `risk_and_evidence`：风险提示、报案后行为、证据保存和补充材料。

每个域由三部分在运行时组合：

- 公共提示词：统一规定锚点、禁止推测、明确否定的处理方式和逐项返回要求。
- 域提示文件：只描述该域边界、字段含义和最容易误判的规则。
- `domain-contracts/*.json`：定义该域的事实路径、值类型、实体字段，并自动生成严格 JSON Schema。

这三部分不是临时由模型自由编写。公共模板、域提示和合同文件都预先保存在仓库中；运行时只把当前文档证据、域定义和 Schema 填进去。

## 3. JSON Schema 与重试

事实抽取请求始终使用：

- `response_format.type=json_schema`
- `strict=true`
- `enable_thinking=false`
- `temperature=0`
- 禁止 plain JSON 和 tool fallback

重试按域进行，不按字段进行。健康路径是 6 个请求，每个域一次。只有以下情况重试：

- 网络、连接、超时或 HTTP 5xx：按 `QWEN_TRANSIENT_RETRIES` 重试。
- JSON 解析、Schema、Pydantic 或域语义校验失败：按 `QWEN_SCHEMA_RETRIES` 重试，并把上次失败详情附到同一域的新提示词中。

成功域不会因为另一个域失败而重跑。重试耗尽后记录具体失败域和错误详情，任务不能伪装成完成。系统不会通过降级到低约束输出掩盖错误。

模型返回之后还有服务端归一化和校验：检查事实路径是否完整、值类型是否正确、锚点是否存在、实体字段是否匹配合同，以及不同域之间是否返回重复路径。Schema 解决的是结构合法性，不等于事实语义一定正确。

## 4. 三十四条规则如何判定

34 条规则使用合并后的约 80 个事实和重复实体做确定性计算，不再让模型直接输出“已通过/未询问”等最终状态。每条规则按以下顺序执行：

1. `appliesWhen`：条件明确为 false 时是“规则不适用”；条件无法确认时是“待人工判断”。
2. `requiredFields`：真正影响结论的主字段。事实缺失、回答含糊或没有有效值时才阻断；规则声明允许明确作答的字段中，`false`、无、否、不适用都是有效回答。
3. `advisoryFields`：流水号、完整地址或条件详情等辅助字段，缺失只形成提示，不把已清楚回答改成“回答不清”。
4. `repeatEntity`：逐笔检查转账、取现、线下交付和联系切换等实体，必要字段才阻断，辅助字段仍是提示。
5. `consistencyChecks`：检查金额合计、返款后净损失、时间顺序和声明数量与实体数量是否一致。

状态优先级为：不适用/待人工判断先由适用条件决定；适用规则中，明确冲突优先为“事实矛盾”，其次判断未询问或回答不清，全部必要条件清楚且一致才是“已通过”。

`questionPatterns` 用完整 QA 判断“问题完全不存在”和“问题存在但答案为空”。当前 33 条问答类规则均已配置该字段，并支持忽略空白、常见标点差异和同义词备选；非问答类规则继续依据事实和适用条件判断。

## 5. 结果、证据与人工处置

规则结果保持六类：已通过、未询问、回答不清、事实矛盾、规则不适用、待人工判断。每条结果保存证据锚点，前端展开的是完整 QA 证据，不再只截取问题句；高亮使用 QA 对应的全部原始段落 ID。

任务存储同时保留解析文档、被害人信息、域抽取载荷、34 条规则结果、耗时和失败域。前端显示六类汇总、被害人卡片和逐条审查，并支持补问、人工处理和归档。

## 6. 当前能力边界

- DOCX 正文图片和表格内图片可以识别并按正文位置参与 QA；页眉/页脚图片仍按兼容路径附后。
- 图片中文字的准确性取决于多模态模型。图片转写接口目前使用提示词 JSON 加服务端字段校验，不使用严格 JSON Schema，也没有独立重试配置。
- 表格原生文本已支持；复杂合并单元格主要保留为行文本，不能保证还原视觉表格结构。
- 模型可以返回完全合法的 JSON，但仍可能把详细答案抽成 `unknown`。服务端只归一化已知且可安全确定的偏差，不会用猜测覆盖模型结果。
- 当前样例验证能证明结构稳定和已覆盖场景正确，不能据此给出真实业务文档上的可信准确率百分比；准确率需要人工标注的多格式语料集计算。
