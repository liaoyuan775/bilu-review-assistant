# 公安智能笔录审查助手产品需求文档 V0.1

> 文档状态：V0.1 原型定稿  
> 编制日期：2026-07-16  
> 产品名称：公安智能笔录审查助手  
> 当前交付：React 前端、Python FastAPI 后端、Qwen 适配器、演示规则与接口文档  
> 原型目标：验证“电子笔录输入 - 内部规则审查 - 漏问问题输出 - 人工处理”闭环

当前实现采用独立前后端结构。无模型网络时可使用 01 号快速模拟案例验证完整交互；02–07 与真实上传均通过后端 OpenAI 兼容接口调用 Qwen，模型不可达或返回无效结果时不保留部分结论。

## 1. 文档结论

一期产品应定位为**民警问审结束后的单份笔录复盘工具**，而不是自动办案系统或法律结论生成器。

产品接收一份规范电子笔录，依据公安业务方提供并确认的规则，识别笔录中已覆盖、提问遗漏、回答不完整和不适用的事项，展示对应规则、原文证据及建议补问方向，最终由民警人工确认。

原型只验证四件事：

1. 能读取规范电子文档并形成可定位的文本；
2. 能按可追溯规则逐项检查，而非让模型自由发挥；
3. 能区分“已覆盖”“提问遗漏”“回答不完整”和“不适用”；
4. 每个结论都能回到规则和笔录原文，方便民警复核。

文档解析失败、审查服务异常或证据不足时，系统终止当前任务并说明原因，不生成部分审查结果，也不把异常伪装为第五种规则状态。

## 2. 需求背景

现场调研已确认一期建设方向：接收电子问审文档，依据公安内部规范化问审标准，梳理已询问事项与遗漏事项，向基层民警提供复盘提示。当前尚未确认具体规则名称、完整检查细项和最终验收口径。

百度千帆“公安智能笔录审核助手”案例可作为流程参考。该案例采用多节点分项检查，再汇总不合规项，涉及笔录头、事件经过、网络账号与聊天记录、转账、APP、快递、返利提现和相关人员等类别。本项目只借鉴其**分层检查思路**，不直接把案例规则或提示词视为公安业务方的正式规范。

## 3. 产品目标与非目标

### 3.1 一期目标

- 将单份电子笔录转为结构化、可定位的问答内容；
- 按业务方规则输出遗漏和不完整事项；
- 提供原文证据、规则依据、建议补问方向和人工复核入口；
- 形成可演示、可继续补充规则的前端原型；
- 用真实脱敏样例验证规则覆盖率和结果可解释性。

### 3.2 一期非目标

- 不替代民警作出执法、定性、立案或证据效力判断；
- 不自动修改原始笔录，不直接生成正式法律文书；
- 不根据模型常识自行补充公安内部规则；
- 不承诺扫描件、手写件、图片型 PDF 的 OCR 质量；
- 不处理批量文档或多案串并分析；
- 不建设完整知识库、智能问答、模型厂商管理和综合首页大屏；
- 不在未确认部署与保密方案前上传真实敏感笔录到公网模型服务；
- 不把模型结果直接作为民警考核、责任认定或自动退回依据。

## 4. 用户与使用场景

### 4.1 核心用户

- **基层办案民警**：上传笔录，查看漏问和不完整事项，补充询问后人工确认；
- **审核/督察人员**：复核审查结果，关注规则命中和高风险遗漏；
- **规则管理员（后续）**：维护内部规则、适用案由、版本和启停状态。

### 4.2 核心场景

民警完成一轮询问后，将规范电子笔录上传。系统识别笔录内容，先检查通用必问项，再根据案情线索触发场景规则，最后输出审查清单。民警可点击任一问题查看原文位置，决定补问、标记已核实或忽略并填写原因。

## 5. 一期输入与输出

### 5.1 输入约束

| 项目 | V0.1 默认方案 |
|---|---|
| 文件类型 | DOCX、文本型 PDF |
| 文档数量 | 单次 1 份 |
| 页数 | 不设固定页数限制，受 20 MB 文件大小和模型上下文能力约束 |
| 文件大小 | 20 MB 以内 |
| 文档性质 | 规范电子文档，可复制文字；不含手写、扫描和复杂表格 |
| 内容语言 | 简体中文 |
| 数据要求 | 原型演示仅使用虚构或脱敏数据 |

上传后应先进行格式校验。解析失败、空文档、超过页数或疑似扫描件时，应明确提示原因，不能进入“伪审查”状态。

### 5.2 输出对象

每条审查结果至少包含：

| 字段 | 说明 |
|---|---|
| 规则编号/名称 | 结论来自哪条已配置规则 |
| 适用状态 | 已覆盖、提问遗漏、回答不完整、不适用 |
| 问题分类 | 通用要素、事件经过、网络账号、转账记录等 |
| 问题描述 | 简明说明缺失或不完整内容 |
| 原文证据 | 支持该判断的问答原文和页码/段落位置 |
| 判断说明 | 为什么命中，避免只给结论 |
| 建议补问 | 供民警参考的补问方向，不自动写入原笔录 |
| 人工处理 | 待处理、确认问题、加入补问清单、忽略 |

### 5.3 结果状态定义

- **已覆盖**：笔录中的询问和回答满足规则要求；
- **提问遗漏**：规则适用，但笔录中未找到对应询问或必要回答；
- **回答不完整**：已询问，但缺少规则要求的关键字段；
- **不适用**：没有触发该场景规则，不应显示为漏问。

规则结果只允许使用这四种状态。文档无法可靠解析、模型调用失败或现有证据不足以支撑规则结论时，任务进入失败状态并提示人工检查，不返回该任务的部分规则结果。

## 6. 规则体系建议

### 6.1 规则分层

1. **基础完整性规则**：所有笔录均需检查，例如时间、地点、人员基本信息、权利义务告知、事件经过等；
2. **场景触发规则**：仅在文本出现相关事实时检查，例如网络平台、转账、下载 APP、寄递、返利提现、第三方人员等；
3. **案由专项规则**：按业务方确认的案由加载，原型可只配置一种案由；
4. **汇总规则**：去重、合并同类问题，生成面向民警的审查清单。

### 6.2 单条规则数据结构

每条规则不应只有一段提示词，建议至少配置以下内容：

```json
{
  "ruleId": "TRANS-001",
  "name": "逐笔转账信息完整性",
  "version": "1.0",
  "category": "转账记录",
  "appliesWhen": "笔录中存在转账或支付行为",
  "requiredFacts": ["时间", "金额", "对方账户", "流水号或交易单号"],
  "passCondition": "每笔转账均覆盖必要事实",
  "severity": "待业务确认",
  "suggestedQuestion": "请逐笔说明转账时间、金额、收款账户及交易单号。",
  "source": "待填写正式规范名称及条款"
}
```

### 6.3 首批演示规则建议

为保证当天可演示，建议先选择 8 至 12 条有明确判定条件的规则，不追求一次覆盖全部规范：

- 笔录基本要素是否完整；
- 权利义务告知是否完整；
- 事情经过是否包含时间、地点、人物和关键行为；
- 涉及网络平台时，账号和聊天记录是否询问；
- 涉及转账时，每笔时间、金额、账户、流水号是否完整；
- 涉及 APP 时，名称、下载来源、账号及当前状态是否询问；
- 涉及寄递时，快递公司、寄件信息和单号是否询问；
- 涉及返利提现时，方式、账户、金额和明细是否询问；
- 涉及第三方人员时，身份及关系信息是否询问。

以上仅是参考案例中的演示分类，必须由业务方确认后才能成为正式规则。

## 7. 核心业务流程

```mermaid
flowchart LR
    A[上传单份电子笔录] --> B[格式与页数校验]
    B -->|失败| C[提示原因并终止]
    B -->|通过| D[解析页码、段落和问答]
    D --> E[执行基础规则]
    E --> F[识别场景并加载条件规则]
    F --> G[规则逐项审查]
    G --> H[证据校验与合并去重]
    H --> I[展示结果及原文证据]
    I --> J[民警人工确认或补问]
```

### 7.1 关键处理约束

- 文档解析结果要保留页码、段落和问答顺序；
- 演示目录固定为七份真实 DOCX；01 返回明确标识的模拟结果，02–07 走 Qwen 完整审查，客户端不能自行切换执行模式；
- 模型只能在已启用规则范围内判断，不能新增规则；
- 每条“提问遗漏/回答不完整”必须有规则依据；
- “已覆盖”应提供命中的原文证据，“未找到”应说明检索范围；
- 文档解析、模型调用或证据校验失败时终止任务，不输出部分结论；
- 汇总阶段只负责去重与归类，不得改变分项检查事实。

## 8. 数据接口与状态约定

V0.1 不对外提供公共开放接口，本节定义前端与审查服务之间的最小数据契约。接口实现可以随技术栈调整，但状态值和业务含义不得改变。

### 8.1 任务状态

| 状态值 | 中文状态 | 含义 |
|---|---|---|
| `uploading` | 上传中 | 文件正在上传，尚未开始解析 |
| `parsing` | 解析中 | 正在校验格式并提取页码、段落和问答 |
| `checking` | 审查中 | 正在执行基础规则、条件规则和证据校验 |
| `completed` | 已完成 | 全部启用规则均已形成有效结果 |
| `failed` | 处理失败 | 格式、解析、模型或证据校验异常，当前任务不返回部分结果 |

失败任务应返回可识别的错误类型，包括 `unsupported_format`、`file_too_large`、`empty_document`、`scanned_pdf`、`parse_failed`、`review_service_failed` 和 `insufficient_evidence`。前端依据错误类型展示重新上传、检查文档或稍后重试等操作。

### 8.2 规则结果与人工处理

规则状态固定为 `covered`、`missing`、`incomplete`、`not_applicable`，分别对应已覆盖、提问遗漏、回答不完整和不适用。人工处理状态固定为 `pending`、`confirmed`、`supplemented`、`ignored`，分别对应待处理、确认问题、加入补问清单和忽略。三种人工处理均为本次复核的已分流终态，不强制用户输入文字。

单条规则结果至少包含以下字段：

```json
{
  "ruleId": "TRANS-001",
  "ruleName": "逐笔转账信息完整性",
  "category": "转账记录",
  "status": "incomplete",
  "missingFacts": ["交易流水号"],
  "evidence": "问：你向对方转了多少钱？答：我转了4600元。",
  "evidenceLocation": { "page": 4, "paragraph": 18 },
  "reason": "笔录已记录转账金额，但未记录交易流水号或交易单号。",
  "suggestedQuestion": "请说明该笔转账的交易流水号或交易单号。",
  "manualDecision": {
    "status": "pending",
    "reason": ""
  }
}
```

模型只能返回当前启用规则的 `ruleId`。服务端应拒绝未知规则、非法状态、缺少必要证据的完成结果，以及忽略原因为空的人工处理请求。

## 9. 功能清单与优先级

### P0：当天原型必须具备

| 模块 | 功能 | 验收要点 |
|---|---|---|
| 新建审查 | 拖拽/选择文件、格式校验、提交分析 | 失败原因清晰，不能提交无效文件 |
| 解析预览 | 显示文件名、页数和解析文本 | 能查看完整文档并定位段落 |
| 审查进度 | 解析中、规则检查中、汇总中、完成、失败 | 状态可见，不使用假进度 |
| 审查概览 | 显示已覆盖、提问遗漏、回答不完整、不适用数量 | 数量与列表一致 |
| 问题清单 | 按类别/状态筛选，展示规则和问题 | 每条问题可展开 |
| 证据联动 | 点击问题，高亮对应原文 | 无证据时明确标记 |
| 人工处理 | 确认问题、加入补问清单、忽略 | 三选一完成分流，处理状态可回看 |
| 演示数据 | 内置 7 份脱敏 DOCX | 01 可快速复现完整效果，02–07 验证真实模型链路 |

### P1：原型完成后补充

- 审查记录列表与再次查看；
- 导出审查报告为 PDF/DOCX；
- 规则版本展示和按案由选择规则集；
- 人工修改模型结论并形成反馈；
- 失败重试和更完整的操作日志。

### P2：正式建设阶段

- 规则管理、灰度发布、版本回滚和权限审批；
- 单位、角色、数据权限和审计日志；
- 内网模型/服务接入、数据脱敏、加密和留存策略；
- 批量审查、质量统计和规则命中趋势；
- 与现有办案系统或内部服务接口集成；
- 在授权前提下建设知识库、智能问答等扩展能力。

## 10. 页面信息架构

### 10.1 一期导航

- **新建审查**：上传文件并启动任务；
- **审查结果**：查看当前任务的原文、问题和人工处理状态；
- **审查记录**：P1 预留；
- **规则管理**：P2 预留，仅显示入口或关闭状态，不在原型中实现完整后台。

首页数据大屏、文件内容识别、智能问答、模型管理和厂商管理均不进入一期主导航，避免演示重点被平台能力分散。

### 10.2 核心结果页布局

建议桌面端采用高密度双栏工作台：

```text
┌──────────────────────────────────────────────────────────────┐
│ 文件名 / 规则版本 / 审查状态 / 重新审查 / 导出（预留）       │
├──────────────────────────────┬───────────────────────────────┤
│ 原文预览 55%                 │ 审查结果 45%                  │
│ 页码、搜索、段落定位         │ 数量概览、筛选、问题列表      │
│ 点击结果后高亮证据           │ 规则、缺失项、建议补问、处理  │
└──────────────────────────────┴───────────────────────────────┘
```

该布局比单纯输出一段总结更适合审查工作：民警无需来回切页，即可对照结论与原文。

## 11. 前端视觉风格分析与建议

### 11.1 参考图片的共同风格

五张图片属于典型的**浅色政务/企业后台管理系统**：

- 白色主界面配浅灰蓝工作区，蓝色作为主要操作和选中状态；
- 固定左侧导航、顶部工具栏和多标签页，强调多任务工作台；
- 细边框、轻阴影、4 至 8 px 小圆角，整体克制、理性；
- 使用线性图标和少量蓝、绿、橙、紫语义色区分状态；
- 表格、上传区、状态卡片和空状态占主导，信息结构标准化；
- 中文字号偏小、页面密度中等，适合办公场景；
- 品牌装饰很少，重点是功能识别和快速操作。

可将其风格概括为：**清爽、可信、工具化、低装饰、蓝色政务科技感**。

### 11.2 不建议原样照搬的部分

- 左侧导航、顶部页签和面包屑同时存在，层级重复；
- 首页指标卡、大面积空图表与当前审查主任务关系弱；
- 多个页面分别提供上传能力，入口显得分散；
- 智能问答页使用较大装饰性浅蓝背景，降低了专业任务密度；
- 模型、厂商和知识库配置直接暴露，会让业务演示变成平台演示；
- 空白区域偏多，审查结果与原文没有形成强联动。

### 11.3 本项目推荐视觉方向

保留参考图片的基础语言，但调整为更安静、严谨的“审查工作台”：

| 视觉项 | 建议 |
|---|---|
| 主色 | 公安科技蓝，建议 `#1677FF`；深色文字 `#17233D` |
| 背景 | 页面 `#F4F7FA`，内容区白色，不使用大面积渐变 |
| 状态色 | 红=提问遗漏，橙=回答不完整，绿=已覆盖，灰=不适用 |
| 圆角 | 4 至 6 px，避免过度卡片化 |
| 边框 | `#E3E8EF` 1 px，阴影只用于弹层和浮动工具 |
| 字体 | 系统中文字体；正文 14 px，辅助 12 px，页标题 20 至 24 px |
| 密度 | 默认紧凑，可在后续预留舒适/紧凑密度切换 |
| 图标 | 统一线性图标；按钮使用图标或图标加短文本 |
| 动效 | 只用于上传、进度、证据定位和状态反馈，150 至 200 ms |

核心结果页不使用营销式大标题、渐变背景或装饰图。审查问题应以分组列表或紧凑表格展示，不把每一条问题都做成大卡片。

### 11.4 风格与功能扩展预留

前端可通过以下方式预留未来变化，而无需现在实现额外页面：

- 颜色、字号、间距、圆角均使用设计 Token；
- 顶部显示 Qwen 实时连通状态，新建审查页明确展示当前审查模式；
- 导航项由权限和功能开关控制，后续可加入知识库、问答和统计；
- 审查结果组件与规则分类解耦，新增案由只增加配置；
- 预留单位标识、系统名称和主题色配置，支持后续公安内网品牌规范；
- 原文查看器预留 PDF 和 DOCX 两种渲染器；
- API 层预留本地模型、内网模型服务或批准后的厂商模型适配器。

## 12. 原型验收建议

### 12.1 演示样例

准备七份覆盖基本完整、明确漏问、APP 返利、冒充公检法、投资交友、冒充客服、线下取现与寄递黄金等场景的脱敏 DOCX。01 为明确标识的快速模拟案例；02–07 必须运行真实 Qwen 审查。

### 12.2 验收口径

- 规范电子文档上传成功率 100%（基于约定样例集）；
- 约定样例能够完整解析并按页/段定位；
- 所有问题项均能关联规则，提问遗漏项能说明未满足字段；
- 不适用规则不计入遗漏数量；
- 四种规则状态的概览数量与结果清单完全一致；
- 解析失败、模型异常或证据不足时任务失败，且不展示部分审查结论；
- 点击审查问题可定位并高亮原文证据；
- 人工处理支持确认问题、加入补问清单和忽略，且不强制输入文字；
- 常规单份文档目标处理时间不超过 60 秒，具体以文档大小和部署模型实测为准；
- 页面在 1440 x 900 及 1920 x 1080 下无关键内容遮挡；
- 原型演示全过程不使用未脱敏的真实案件数据。

## 13. 数据安全与责任边界

- 原始笔录属于高敏感业务数据，原型阶段只允许使用虚构或脱敏材料；
- 正式接入前必须确认部署位置、模型调用链、传输加密、存储加密、日志脱敏、数据留存与删除机制；
- 若使用外部模型服务，必须先取得业务方和安全管理方明确批准；
- 模型输出需要记录规则版本和模型版本，便于追溯；
- 操作日志不能完整记录身份证号、手机号、银行卡号等敏感原文；
- 产品界面应持续提示“智能审查结果仅供复盘参考，以人工审核为准”。

参考案例中出现的“无需关心账户暴露等隐私问题”不应进入本项目设计。真实公安场景必须把隐私保护和可审计性作为前置条件。

## 14. 待业务方确认清单

以下问题会直接影响原型验收，建议按优先级尽快确认：

已经确认的原型口径不再列为待确认项。后续仍需公安业务方提供或确认以下内容：

1. 首个演示案由及其正式名称；
2. 8 至 12 条正式或暂定规则，以及每条规则的来源和合格条件；
3. 七份脱敏样例的预期漏问项及业务验收口径；
4. 问题是否需要严重程度、退回等级或必改标识；
5. 后续报告导出格式及现有模板；
6. 正式系统的数据保存期限、可见范围和删除机制；
7. 模型与应用部署在内网、政务云还是其他批准环境；
8. 现有办案系统的接口范围及审批结果；
9. 人工处理反馈是否沉淀为规则改进数据。

## 15. 建议的当天交付范围

为了让原型“看得懂、跑得通、能讨论”，建议当天只交付：

- 1 个双栏审查结果页；
- 1 套包含 8 至 12 条规则的演示规则配置；
- 7 份脱敏演示文档；
- 可复现的已覆盖、提问遗漏、回答不完整和不适用状态；
- 可复现的格式错误、扫描件、解析失败和审查服务异常提示；
