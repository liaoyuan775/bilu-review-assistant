# 交互执行流程与测试笔录设计

## 目标

在现有笔录审查助手中新增可交互的业务执行流程页面，并提供三份可直接上传的正式排版 DOCX 测试笔录，用于第一版现场演示和规则验证。

## 交互执行流程

- 在侧边导航新增“执行流程”，与“新建审查”“审查结果”处于同一层级。
- 页面使用 React Flow 构建，支持画布拖拽、滚轮缩放、控件缩放、自动适配和节点点击。
- 主链路固定为：文件校验、文本解析、问答定位、通用规则检查、条件规则触发、模型规则审查、证据校验与汇总、人工处理。
- 文件校验、文本解析、模型规则审查和证据校验均连接失败分支，失败任务不生成部分规则结论。
- 点击节点后，右侧详情区展示节点目的、输入、处理、输出和异常；当前节点在画布与详情区同步高亮。
- 页面沿用现有浅色政务工作台视觉，不新增大屏、渐变或装饰性卡片。

## 测试笔录

三份文档均采用正式询问笔录结构，包括标题、虚构材料标识、案号、询问时间地点、询问人、记录人、被询问人身份、权利义务告知、连续问答和签名栏。

1. `01-基本完整-电诈询问笔录.docx`：身份、网络账号、APP、逐笔转账、聊天记录和电子证据均有明确回答。
2. `02-明确漏问-电诈询问笔录.docx`：保留真实问答语气，但有意不询问部分必问项和场景字段，用于产生明确遗漏。
3. `03-复杂场景-APP返利询问笔录.docx`：覆盖 APP、转账、返利、第三方人员和电子证据，并包含少量被询问人明确回答“我不知道”的字段。

所有姓名、身份证号、手机号、住址、单位、微信、QQ、APP 账号、银行卡、支付账户、流水号、IP 和链接均为虚构测试值。未知信息只能通过完整问答表达，例如“问：对方真实姓名是什么？答：我不知道。”，文档中不得出现“待补充”“XXX”或未解释的空白占位。

## 实现边界

- 前端流程图使用 `@xyflow/react`，流程数据与页面组件分离。
- DOCX 使用 `python-docx` 生成，生成脚本可重复执行并稳定覆盖同名文件。
- 三份测试文档仅供系统功能测试，页眉与正文均明确标注“虚构测试材料”。
- 不新增历史保存、正式报告导出或规则编辑能力。

## 异常与安全

- 流程图详情明确展示 `failed` 路径和“不返回部分伪结果”约束。
- 测试文档不得使用真实单位名称、真实人员信息或可访问的真实业务链接。
- IP 使用文档保留地址段，链接使用 `.test` 保留域名，账号包含 `test` 或固定演示编号。

## 验证

- 单元测试校验流程节点、主链路顺序、失败分支和节点详情字段。
- 单元测试打开三份 DOCX，校验正式结构、虚构材料标识、关键模拟字段和“我不知道”的使用约束。
- 前端执行 TypeScript 构建，后端执行完整 pytest。
- 使用 Microsoft Edge 验证流程图导航、缩放、节点点击和详情联动。
- 将三份 DOCX 转为 PDF/图片并逐页检查；若本机缺少 LibreOffice，则使用 Word 自动化导出 PDF 后检查。
