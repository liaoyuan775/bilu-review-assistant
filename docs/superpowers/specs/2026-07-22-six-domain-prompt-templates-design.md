# 六域提示词语义增强设计

## 目标

在不改变严格 JSON Schema、域合同、6 域并发和规则引擎的前提下，把目前每个域约 3 条的补充说明扩展为可独立理解的域语义模板，减少清晰回答被误判为 `missing`、跨域重复抽取和从无关事实推断结论的问题。

## 当前结构

运行时由 `backend/app/review/domain_contract_rendering.py::render_domain_prompt` 合并：

1. `backend/prompt-templates/domain-extraction.txt`：公共硬约束。
2. `backend/prompt-templates/domains/<domain>.txt`：域专项说明。
3. `backend/domain-contracts/<domain>.json`：字段、类型、边界和实体合同。
4. 当前文档的结构文本、完整问答、锚点和上次校验反馈。

当前最终请求已经按域不同，但域专项说明偏短，公共模板仍承担了大部分语义指导。

## 方案比较

### 方案 A：复制 6 份完整提示词

每个域包含全部公共约束、字段说明和域语义。优点是单文件直观；缺点是 Schema、锚点和 `clarity` 规则会重复六次，后续容易漏同步或出现冲突。

### 方案 B：公共硬约束 + 6 份完整域语义模板（采用）

公共模板只保留所有域必须一致的输出协议；每个域文件完整描述该域的业务目标、边界、判断方法和禁止推断。域合同继续自动生成字段清单及 JSON Schema。

该方案保留单一技术约束来源，同时让模型在每个域获得足够具体的语义指导，改动范围最小。

### 方案 C：只依赖域合同描述

继续缩短自然语言提示词，让模型主要依赖 JSON Schema 字段描述。维护成本最低，但 Schema 擅长限制结构，无法充分表达明确否定、空答、跨域排除和业务推断边界，因此不采用。

## 文件职责

### 公共模板

`backend/prompt-templates/domain-extraction.txt` 继续统一负责：

- 只抽取证据事实，不判断规则状态。
- `clarity` 四值及锚点要求。
- 模板说明、电子方框和空答案处理。
- 重复实体、实体 ID 和禁止额外字段。
- 上次 Schema 校验反馈、结构文本和完整问答占位符。

公共模板不写任何单一业务域的字段判定。

### 域语义模板

6 个 `backend/prompt-templates/domains/*.txt` 统一使用以下小节：

1. `本域目标`：该请求应回答的业务问题。
2. `包含与排除`：强调跨域边界，不复制域合同的全部字段列表。
3. `clarity 判定`：本域中明确回答、模糊回答、无法判断和未提供信息的区别。
4. `字段与实体规则`：核心字段、辅助字段、适用条件和重复实体处理。
5. `禁止推断`：列出已发现的典型错误推断。

域模板不重复 JSON Schema，不硬编码服务端锚点枚举，不增加规则状态词，不包含真实个人信息或真实案件原文。

## 六域增强重点

### `header_procedure`

- 区分“已阅读告知书”“没有额外要求”和“未回答”。
- 明确“无、否、不申请回避”是清晰否定。
- 结构区已有姓名可复用，不重复创建字段。
- 不从签名存在推断所有程序告知均已完成。

### `case_timeline`

- 保留报案原因、诈骗方式、连续经过、时间地点、隐私泄露、付款和持续联系原因。
- 案发地点按合同中的完整地点一次抽取，不拆回省市区街道多字段。
- “没有补充”是 `clear`；空答是 `missing`。
- 不重复抽取联系账号、逐笔资金、总损失和返款。

### `contact_channels`

- 电话、短信号码或聊天账号都可作为有效联系标识。
- 只有明确使用聊天软件才返回 `true`；无法确认返回 `unknown`。
- 联系切换逐次生成实体，不把多个联系人合并。
- 不从存在电话号码推断使用过聊天软件或账号实名。

### `risk_and_evidence`

- 明确“无、否、未收到”是清晰事实。
- 录音问题空答时不得根据发生过通话推断存在录音。
- 聊天工具、实名或材料是否可提供无法确认时返回 `unknown`。
- 不把“知道反诈”推断为“收到过具体预警”。

### `online_money`

- 金额、笔数和逐笔金额按原文抽取，不在模型层修正矛盾。
- 逐笔转账实体不合并；流水号为辅助字段。
- 返款只抽取合同保留的汇总字段。
- 不从总损失反推转账笔数或逐笔金额。

### `offline_delivery`

- 银行、网点和完整地点分别按合同抽取，完整门牌地址为辅助信息。
- 取现和线下交付分别逐次创建实体。
- 明确没有邮寄、物流或线下交付时返回清晰否定。
- 不从“取现”自动推断现金已交给对方，也不从“购买黄金”推断已经交付。

## 数据流与错误处理

运行时拼装方式保持不变：公共模板注入对应域语义、域合同、当前证据和上次失败反馈。`build_domain_schema`、`request_structured_payload`、Pydantic 校验、锚点校验和域级重试均不改动。

提示词增强不会新增 fallback、额外模型请求或字段级重试。Schema/JSON 校验失败仍按 `QWEN_SCHEMA_RETRIES` 在失败域内重试；可安全降级的域失败仍映射为 `needs_manual_review`。

## 测试策略

先增加模板结构测试并确认失败，再修改 6 个域文件：

1. 每个域模板必须包含五个固定小节。
2. 每个域最终渲染提示词必须包含自己的语义模板，不包含其他域的专项内容。
3. 公共严格约束在渲染结果中只出现一次。
4. 6 个域生成的 JSON Schema 与修改前保持一致。
5. 运行域合同、提示词渲染和事实抽取聚焦测试。
6. 使用 `06-all-statuses-demo.docx` 做一次真实审查，记录完成状态、34 条结果、失败域、Schema 重试次数和耗时；不把单文件结果声明为整体准确率。

## 验收标准

- 6 个域文件均能脱离公共模板单独说明本域判断逻辑。
- 公共模板、域合同和 Schema 生成代码不重复、不分叉。
- strict JSON Schema、`enable_thinking=false`、6 域并发和现有重试配置保持不变。
- 聚焦自动化测试全部通过，前端不需要改动。
- 真实样例可完成审查并产出 34 条结果；如发生误判，记录具体域、字段、原文证据和模型 `clarity`，不增加新的关键词补丁。

## 非目标

- 不修改 34 条规则及六类状态定义。
- 不新增模型二次裁判、字段级重试或 plain/tool fallback。
- 不按关键词裁剪完整问答，避免格式变化导致关键证据被提前过滤。
- 不承诺仅通过提示词修改即可达到固定业务准确率。
