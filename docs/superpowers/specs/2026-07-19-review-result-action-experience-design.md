# 审查结果人工处置体验优化设计

## 背景

当前审查结果页将“未询问、回答不清、事实矛盾、待人工判断”统一展示为四个动作：确认问题、记录补问、确认不适用、忽略。四类问题的业务含义不同，但按钮完全相同；其中“确认问题”只写入人工状态，既不解决问题，也不能解除高风险归档限制，容易让使用者误以为已经完成处置。

顶部五类统计表示自动审查结论，人工动作不会直接改写这些结论。只有保存补问答案并触发相关业务域重审后，自动结论才可能变化。界面需要明确区分“自动审查状态”和“人工处置结果”。

## 目标

1. 为四类异常结果提供符合其语义的主操作。
2. 删除新界面中含义模糊的“确认问题”，保留后端历史状态兼容。
3. 让每次操作的直接结果和归档影响在界面上可理解。
4. 所有异常项都必须闭环后才能归档，不再只要求高风险项闭环。
5. 提供一份面向使用者的快速上手文档。

## 非目标

- 不改变自动规则引擎对 `RuleStatus` 的计算方式。
- 不删除历史数据中的 `ManualStatus.CONFIRMED`。
- 不修改原始上传文件。
- 不把本地归档扩展为外部档案系统或具有法律效力的电子归档。

## 操作模型

异常项的终态只有三种：

- `resolved`：事实已经通过补问重审，或人工核对后明确接受现有材料；
- `not_applicable`：人工确认本案不适用，必须填写依据；
- `ignored`：明确决定不处理，必须填写依据。

`supplemented` 表示已经加入补问、但尚未记录答案并完成重审，不是闭环状态。历史 `confirmed` 同样不是闭环状态。

### 各类别操作

| 自动类别 | 主操作 | 次要闭环操作 | 说明 |
|---|---|---|---|
| 未询问 | 补问并重审 | 确认不适用；不处理并说明 | 原文没有明确问答，不能“接受现有回答” |
| 回答不清 | 补问并重审 | 接受现有回答；确认不适用；不处理并说明 | 接受现有回答必须说明为何现有内容已经足够 |
| 事实矛盾 | 核实并重审 | 确认以现有材料为准；确认不适用；不处理并说明 | 人工直接闭环时必须说明采用哪项材料及理由 |
| 待人工判断 | 确认适用并补问 | 确认不适用；不处理并说明 | 适用性不明时不提供笼统“确认问题” |
| 已覆盖 | 无操作 | 无 | 只展示证据和自动结论 |

自动状态为 `not_applicable` 的规则也只展示，不要求再次处置。

### 动作文案与状态映射

| 界面动作 | 保存状态 | 是否要求依据 | 是否闭环 |
|---|---|---:|---:|
| 补问并重审 / 核实并重审 / 确认适用并补问 | 先保存 `supplemented`，记录答案后保存 `resolved` | 补问和答案必填 | 记录答案并重审后才闭环 |
| 接受现有回答 | `resolved` | 是 | 是 |
| 确认以现有材料为准 | `resolved` | 是 | 是 |
| 确认不适用 | `not_applicable` | 是 | 是 |
| 不处理并说明 | `ignored` | 是 | 是 |

## 界面设计

每条异常详情显示：

1. 自动审查状态、判断说明、缺失字段、证据原文和建议补问；
2. 一行简短的“推荐处理”，解释当前类别为什么推荐该主操作；
3. 一个醒目的状态专属主按钮；
4. 次要闭环按钮，其中需要理由的动作只有填写处理依据后才能提交；
5. 当前人工处置状态和“是否已闭环”提示。

顶部五类数字继续统计自动结论，不因人工点击而伪装成“已覆盖”。补问重审改变规则结果后，统计随新结果更新。归档门禁单独显示“未闭环问题 N”，避免使用者把自动统计和人工进度混为一谈。

点击补问主按钮后立即保存 `supplemented` 并打开补问面板，因此该项会进入补问清单。只有填写实际补问与被询问人回答并执行“保存并重审”后，该项才变为 `resolved`。

## 归档规则

归档前必须同时满足：

1. 自动审查任务完成；
2. 没有失败的抽取业务域；
3. 所有解析告警已确认；
4. 报告 PDF、补问 DOCX、结构 JSON、归档清单均已针对当前版本生成；
5. 所有 `missing`、`incomplete`、`inconsistent`、`needs_manual_review` 项均处于 `resolved`、`not_applicable`，或带有非空依据的 `ignored`。

任意人工处置、补问重审或告警确认都会使旧生成产物失效，需要重新生成后才能归档。归档成功后任务进入只读状态，记录归档时间与审计事件；原件内容不变。

## 实现边界

- 新增一个纯前端操作策略模块，集中维护各状态的推荐说明、主动作标签和允许的次要动作，避免文案散落在组件内。
- `TemplateReviewView` 按策略渲染动作，并展示人工处置结果。
- 前后端归档门禁统一改为“所有异常项闭环”。
- 后端继续接受 `confirmed` 以兼容历史调用，但新界面不再产生该状态。
- 报告和结构化 JSON 继续记录自动结论与人工处置，两者不互相覆盖。

## 错误与边界处理

- 接受现有回答、确认以现有材料为准、确认不适用、不处理时，依据为空则前端阻止提交，后端继续执行必填校验。
- 补问问题或回答为空时不能保存重审。
- 已加入补问但未填写答案的项目继续阻止归档。
- 历史 `confirmed` 项显示为“旧版：仅确认，仍需闭环”，并继续阻止归档。
- 已归档任务保持只读，不显示人工操作按钮。

## 测试设计

1. 前端策略单元测试覆盖五类状态的主操作、次要动作、依据要求和闭环判断。
2. 前端归档门禁测试覆盖所有风险等级的异常项，确认 `pending`、`supplemented`、`confirmed` 均阻止归档，三个终态允许归档。
3. 后端归档生命周期测试覆盖低、中、高风险异常项，确保前后端门禁一致。
4. 前端构建验证 TypeScript 和组件引用正确。
5. 快速上手文档逐项说明按钮、保存状态、顶部统计变化、补问清单变化、产物失效和归档结果。
