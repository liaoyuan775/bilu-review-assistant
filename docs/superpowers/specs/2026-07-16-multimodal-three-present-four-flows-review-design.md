# 多模态三现四流笔录审查设计

## 目标

将现有笔录审查原型改造成面向电信网络诈骗场景的多模态审查流程。系统上传 PDF 或 Word 文档后，先形成带页码、段落和来源信息的标准笔录，再依据固定的“三现四流”工作口径检查漏问、回答不完整和不适用事项，并保留可回到原文的证据。

本功能仍是辅助复盘工具，不作案件定性、法律结论、责任判断或证据效力判断，所有结果均需人工复核。

## 资料来源与使用边界

### 强制规则依据

强制规则由本项目确认的“三现四流”工作口径组成，并参考以下公开材料确定证据组织方式：

- 最高人民检察院《常见电信网络诈骗犯罪的证据审查要点》：https://www.spp.gov.cn/spp/llyj/202412/t20241203_675228.shtml
- 最高人民检察院《跨境电信网络诈骗案取证策略与证据体系构建》：https://www.spp.gov.cn/spp/llyj/202201/t20220129_543282.shtml
- 最高人民法院、最高人民检察院、公安部《关于办理电信网络诈骗等刑事案件适用法律若干问题的意见（二）》：https://www.dejiang.gov.cn/zfbm_5646712/gaj/zcwj_5646907/202106/t20210625_68816181.html

“三现四流”是本项目采用的办案审查工作口径，不在界面或结果中表述为国家统一法定术语。

### 补充提示来源

百度千帆《公安智能笔录审核助手》仅作为提示词补充资料：https://cloud.baidu.com/doc/qianfan/s/Wmh4su1k2

其中涉及的网络账号与聊天、逐笔转账、APP、寄递、返利提现、第三方人员等字段可以帮助模型识别场景、搜索证据和生成建议补问，但不进入强制缺失判定。补充项单独缺失时，不得改变 `covered`、`missing`、`incomplete` 或 `not_applicable` 状态。

不采用该示例中“刻薄纠察”“无需关心隐私”等角色措辞，也不把百度示例标注为公安机关统一规范。

## 文件范围

第一版支持：

- `.pdf`：文本型 PDF、扫描型 PDF、文本与图片混合 PDF。
- `.docx`：正文段落、表格和内嵌图片。
- 单文件最大 20 MB，沿用现有上传限制。

第一版不支持旧版二进制 `.doc`。当前运行环境没有 Word 或 LibreOffice 转换器，直接接受 `.doc` 会产生不可验证的兼容性。界面和错误信息应明确提示用户另存为 `.docx` 或 `.pdf`。

## 总体架构

处理链路分为四个职责明确的阶段：

1. 文件标准化：验证扩展名、大小和文件可读性，按页或内容单元提取原生文字、表格和图片。
2. 多模态补充识别：仅对无可靠文本的扫描页、图片区域和 DOCX 内嵌图片调用当前 `.env.local` 中配置的多模态 Qwen 模型。
3. 固定规则审查：将标准笔录、强制规则和补充提示发送给同一模型，要求输出完整、结构化的规则结果。
4. 程序化校验：校验规则编号、适用性、缺失字段、证据文本、页码段落和结果完整性，通过后才保存结果。

识别和审查必须是两次职责独立的模型调用。识别调用只能转写和组织原文，不得给出审查结论；审查调用只能依据固定规则判断，不得改写原文或新增规则。

## 文件标准化

### PDF

- 使用支持页面渲染和文本提取的 PDF 库逐页处理。
- 原生文本达到质量阈值的页面保留程序提取文本，不进行无意义的二次 OCR。
- 无文本、文本过少或乱码比例过高的页面渲染为图片，交给多模态模型识别。
- 混合页面保留原生文字，同时识别页面中的主要图片区域；合并时去除明显重复内容。
- 加密、损坏或页数无法读取的 PDF 终止任务。

### DOCX

- 提取普通段落，并保持文档顺序。
- 提取表格内容，按行转换为可读段落，保留表格来源标记。
- 提取内嵌图片并交给多模态模型识别。
- DOCX 不使用当前按 1800 字模拟真实页码的方式。由于 DOCX 本身不保存稳定的渲染页边界，结果位置使用“内容单元编号”；界面可以显示逻辑页，但必须标注为逻辑分页。
- 空文档、损坏文档或没有任何可识别内容时终止任务。

### 标准笔录

解析输出统一为 `ParsedDocument`，每个内容单元至少包含：

- `page`：PDF 真实页码或 DOCX 逻辑页码。
- `paragraph`：页内段落编号。
- `text`：保留原意的识别文本。
- `sourceType`：`native_text`、`table` 或 `vision`。
- `confidence`：多模态识别置信提示；原生文本不伪造模型置信度。

识别后的完整文本和位置索引是后续审查的唯一事实来源。模型不得根据常识补写原文没有出现的内容。

## 三现四流强制规则

### 三现

1. 案发现场：受骗时的时间、地点、使用环境、在场人员和关键操作场景。
2. 涉案现物：手机、电脑、电话卡、银行卡、U 盾、涉诈 APP、安装包及其他可提供或已提取的载体。
3. 电子现痕：通话记录、短信、聊天记录、群聊、截图、转账凭证、链接、域名、账号和其他电子痕迹的存在及保存情况。

### 四流

1. 人员流：被害人、对方身份或虚拟身份、介绍人、同事朋友、取现人、寄递人员及相互关系。
2. 信息流：首次接触渠道、平台账号、通信方式、诈骗话术、聊天过程、群聊和信息传递顺序。
3. 资金流：每笔转账时间、金额、付款账户、收款账户、支付渠道、交易流水号、总损失、返利返现、止付冻结和返还情况。
4. 行为流：从引流、建立联系、下载或登录、接受指令、转账、继续充值、提现失败到发现被骗和报案的完整时间线。

规则保存在结构化 JSON 中，每条规则至少包含：

- `id`、`name`、`group`、`scope`。
- `triggers`：条件规则的适用触发事实。
- `requiredFacts`：决定规则状态的强制字段。
- `referenceHints`：只用于辅助理解和补问的提示。
- `evidencePolicy`：证据和位置要求。
- `suggestedQuestion`：缺失或不完整时的建议补问模板。
- `source`：`working_rule` 或 `supplementary_reference` 及来源说明。

## 审查状态

- `covered`：规则适用，全部强制字段均有明确问答或可核验证据。
- `missing`：规则适用，但没有询问或回答任何强制字段。
- `incomplete`：规则适用，已涉及相关事项，但仍缺少一个或多个强制字段，或回答仅为无法核验的模糊表述。
- `not_applicable`：条件规则没有被笔录事实触发。基础规则不得使用该状态。

“不知道”“不记得”“无法提供”属于已经询问但信息未取得。模型应保留原回答并标记为 `incomplete`，不得误判为完全未询问；建议补问可以提示核实其他材料，但不得把未知内容补写成事实。

## 模型提示与输出

### 识别提示

识别提示只要求：

- 按阅读顺序逐字转写可见内容。
- 保留问答标记、账号、金额、日期、流水号、链接及星号遮挡。
- 无法辨认时输出明确占位和低置信提示，不猜测字符。
- 返回与输入页面或图片一一对应的 JSON。

### 审查提示

审查提示由程序拼接：角色边界、状态定义、强制规则、补充提示、标准笔录和 JSON 输出协议。模型必须返回全部启用规则，每条一次，并提供：

- `ruleId`、`status`、`missingFacts`。
- `evidence`、`evidenceLocation`。
- `reason`、`suggestedQuestion`。
- `advisories`：来自补充提示的非强制关注项，不影响规则状态。

## 程序化校验

后端必须在保存结果前检查：

- 结果数量与启用规则一致，规则编号无未知和重复项。
- 基础规则不能标记为 `not_applicable`。
- 条件规则状态与标准笔录中的触发事实一致。
- `missing` 和 `incomplete` 具有明确的强制缺失字段和建议补问。
- `covered` 和 `incomplete` 必须提供有效位置。
- 引用证据能够在对应原文段落中匹配，不能只给概括性结论。
- `advisories` 不参与状态统计和“需人工处理”计数。

任一关键校验失败时，任务整体进入 `failed`，清空规则结果，不降级为部分成功或本地关键词结论。

## 前端行为

- 上传提示改为支持文本型/扫描型/混合 PDF 和 DOCX，单份不超过 20 MB。
- 处理状态区分“解析文件”“识别图像文字”“执行三现四流审查”“校验证据”。
- 结果按“三现”“四流”分组，并保留四种状态统计。
- 强制缺失字段与“补充关注”分开展示，补充关注不得显示为明确漏问。
- 证据点击后定位到 PDF 真实页或 DOCX 逻辑页内容单元。
- 保留确认问题、已补问、忽略并填写原因的人工处理流程。
- 页面明确标注模型辅助、规则工作口径和脱敏材料限制。

## 数据与安全边界

- 原始文件、识别文本、结果和人工决定仍只保存在后端进程内存中，服务重启即清空。
- 原始文件和识别内容会发送到 `.env.local` 配置的模型服务；界面必须在上传区明确要求仅使用脱敏材料。
- 日志不得记录原文、文件二进制、模型请求正文或 API Key。
- 第一版不增加历史任务、数据库、报告导出、批量上传、规则编辑或用户权限系统。

## 错误处理

需要提供稳定错误码并显示可读说明：

- 文件过大、扩展名不支持、旧版 `.doc` 不支持。
- PDF/DOCX 损坏、加密或内容为空。
- 页面渲染失败、图片提取失败、多模态识别失败。
- 模型未配置、不可达、超时或返回非法 JSON。
- 模型漏规则、证据与原文冲突或位置无效。

失败任务不生成规则统计和部分审查结果。

## 测试与验收

自动化测试至少覆盖：

- 文本型 PDF、扫描型 PDF、混合 PDF、纯文本 DOCX、带表格 DOCX、带图片 DOCX。
- 空文件、损坏文件、加密 PDF、旧版 `.doc` 和超过 20 MB 文件。
- 多模态识别成功、低置信内容、服务不可达和非法响应。
- 三现四流的 `covered`、`missing`、`incomplete`、`not_applicable`。
- “不知道”判为已询问但不完整。
- 补充提示产生 `advisories`，但不改变强制规则状态和统计。
- 证据原文匹配、位置校验和失败不返回部分结果。
- 前端上传文案、处理状态、规则分组、证据联动和人工决定。

验收标准：使用至少三份脱敏测试笔录分别覆盖基本完整、明确漏问和复杂混合文档场景；所有规则结果都能定位到原文或明确说明全文未检索到；模型或证据校验失败时任务整体失败。
