# 内部询问笔录全流程审查适配设计

## 目标

将现有电信网络诈骗询问笔录审查工具从固定的“三现四流”七条规则，改造成以内部《电信网络诈骗案件询问笔录（模板）》为唯一规则来源的可追溯审查闭环：上传原件、解析和问答重建、案件事实抽取、条件规则校验、证据定位、问题标记、民警补问处理、报告产出和只读归档。

## 已确认的模板事实

- 模板有 144 个正文段落、32 个段首“问”和 1 个同段嵌入“问”，另有笔录头、签名和阅笔录结构项。
- 模板是下划线式连续段落，不是 Word 表格；问答可能跨段和跨页。
- 实际 Word 导出 PDF 为 8 页，但固定页脚写成“共 7 页”；输出必须动态计算页数。
- 模板同时包含通用必审项、案件条件项和重复明细：渠道切换、多笔转账、多笔返利、多次取款、多次现金/黄金交接。
- 用户已确认开始实施；当前规则解释为：通用项必须有明确问答，条件项先判断适用性，适用后检查明细，不适用必须可解释，语义等价问法允许。

## 设计原则

1. 规则来自模板，不把“三现四流”继续当作最终规范。
2. 模型只抽取有证据的事实和解释，不自行发明规则状态。
3. 程序确定性校验适用性、必填字段、重复数量、金额和时间一致性。
4. 原件、标准化文本、模型快照、规则版本、人工事件和报告产物可回放。
5. 任何自动阶段不完整时禁止生成“完整审查”或归档成功状态。
6. 先锁定质量，再做保持语义结果不变的性能优化。

## 系统数据流

```text
原始 DOCX/PDF
  -> 文件头/MIME/大小/哈希校验与原件保存
  -> 容错解析：物理页/逻辑块/字符范围/问答块/告警
  -> Qwen 业务域 strict-schema 事实抽取（路径 + 重复实体 + 证据锚点）
  -> 版本化模板规则引擎（适用性、字段、计数、金额、时间、一致性）
  -> 定向语义复核（仅含糊、冲突或适用性未知项）
  -> 民警定位、标记、补问、答案回填与受影响域重审
  -> 审查报告 PDF + 补问清单 DOCX + 结构化 JSON
  -> 原件/版本/事件/产物/哈希清单只读归档
```

## 文档解析与定位

`ParsedDocument` 扩展为不可变 `DocumentSnapshot`。每个文档块包含稳定 ID、文档版本、物理页（PDF）或逻辑页（DOCX）、块序号、字符起止偏移、原文、来源类型、置信度和原件锚点。

DOCX 解析直接读取 Open XML 正文、页眉、页脚、内容控件和关系。图片关系单独处理；非关键图片 CRC 损坏时保留正文并生成 `media_warning`，而不是让 `python-docx` 因整包 CRC 失败丢弃全部正文。PDF 保留物理页、文本块和坐标。问答重建识别 `问：`/`问:`、`答：`/`答:`，支持跨段和跨页；模板括号内说明被标记为模板指导，不进入被询问人事实。

证据锚点包含 `documentVersionId`、`page`、`blockId`、`charStart`、`charEnd`，并可附 PDF 坐标。前端用锚点高亮精确范围；无法精确定位时显示块级定位和告警，不能声称字符级准确。

## 事实抽取

抽取按业务域拆分，避免把整份全文重复发送给每个规则分组：

- `header_procedure`: 笔录头、人员信息、告知、回避、阅笔录和签名。
- `case_timeline`: 报案原因、案发时空、首次联系、信息泄露、诈骗经过和主观原因。
- `contact_channels`: 首次引流渠道、后续切换、账号/昵称、电话/短信、群组、网站、APP、物流/外卖。
- `risk_and_evidence`: 反诈宣传、风险提示、挂失、实名、录音和证据留存。
- `online_money`: 总额、转出控制方式、声明笔数、逐笔支付、返利、USDT 和金额关系。
- `offline_delivery`: 取款来源、预约、银行网点、现金/黄金交接、邮寄和面对面交付。
- `special_scenarios`: 赌博、冒充电商物流客服等模板条件项。

所有字段都包含 `value`、`clarity`（明确/不清/未知/缺失）、`evidenceAnchors` 和 `sourceConfidence`。联系人、切换、转账、返利、取款、交接均为带稳定实体 ID 的数组，不能被压成单个字段。

## 规则与状态

规则文件采用版本化 JSON，至少包含：`ruleId`、`name`、`sourceParagraphs`、`scope`、`appliesWhen`、`requiredFields`、`repeatEntity`、`consistencyChecks`、`suggestedQuestion` 和 `severity`。

规则状态为：

- `covered`: 适用且所有必需事实明确、证据有效、一致性通过。
- `missing`: 适用，但没有对应问题或必需字段。
- `incomplete`: 已问或已提取，但字段为空、回答“未知/不记得”或明细不足。
- `inconsistent`: 数量、金额、时间顺序或跨实体引用冲突。
- `not_applicable`: 有明确路径证据证明条件未触发。
- `needs_manual_review`: 模型/解析无法可靠判断，必须人工处理。

解析失败、抽取域失败、证据校验失败是任务级状态，不伪装为规则状态。规则引擎生成 `missingFields`、`reason`、`evidenceAnchors` 和 `suggestedQuestion`，模型不得直接覆盖这些确定性结果。

## 人工闭环

每个问题支持确认、编辑补问、记录实际问题和答案、标记已解决、确认不适用、忽略并填写理由。所有动作以追加事件保存，包括处理人标识（当前 V1 可为本地操作员 ID）、时间、旧值、新值和依据。补问答案创建新的文档版本，只重跑受影响业务域和依赖规则；旧结果保持只读。

归档前必须满足：所有自动阶段成功、所有高风险问题已解决或有完整人工依据、无待确认的证据告警、报告/补问清单/JSON 产物生成成功。归档后任务、事件和产物只读。

## 存储与产出

继续使用本地 SQLite，但从单行 JSON 扩展为明确表边界：`documents`、`document_versions`、`review_runs`、`extracted_facts`、`review_issues`、`manual_events`、`artifacts` 和 `review_tasks` 摘要。原件保存在受控归档目录，数据库保存路径、哈希和元数据。

报告产出包含案件/被害人摘要、适用路径、规则版本、逐项状态、遗漏/不清/矛盾项、精确证据、人工处理轨迹、未解决项和耗时。补问清单使用 `python-docx` 生成，审查报告先生成 HTML 并渲染 PDF；两者都动态计算页数，不复用模板错误的固定总页数。

## 质量验收

建立至少 12 个模板场景基准案，保留现有 7 类场景并补齐电话/短信、USDT、远程控制、现金/黄金、物流、赌博和冒充电商物流客服。每案同时生成 DOCX 和同源文本 PDF，并配套 oracle JSON。

从完整案自动生成删除问题、空答案、“不知道”、重复项缺失、数量/金额/时间矛盾突变案。门槛为：约定 DOCX/PDF 解析成功率 100%；问答块、必审字段、重复实体、证据锚点、适用性和预期问题召回率 100%；完整样例不得出现未解释的高风险误报；同一模型配置连续 3 次的事实、实体数、状态和锚点一致。

所有测试数据、日志、报告和归档执行敏感信息扫描；使用显式测试命名空间，不使用可对应真实人员的完整号码。自动测试之后按民警工作流逐案走查，发现漏问或错误定位即不通过。

## 性能与发布

固定模型、机器和 12 案语料，冷/热进程各测至少 5 次，记录解析、各抽取域、规则、定向复核、产出、归档和总耗时的 P50/P95、请求数和 token。候选优化为文档版本内缓存、路径裁剪、有限并发、域级上下文裁剪、确定性项跳过复核和连接复用。

只有所有质量门槛保持通过，且首次审查 P50 或 P95 有至少 10% 可重复改善，才合入优化；缓存命中不能冒充首次审查提速。

在隔离 worktree 的 `codex/template-complete-review` 分支开发，阶段性提交并推送同名远端分支。最终获取最新 `origin/main`，通过完整测试、浏览器流程、文档渲染、安全扫描和性能对比后合并并推送 `main`。
