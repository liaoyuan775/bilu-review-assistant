# 电诈笔录阶段审查与民警反馈闭环 V1 设计

> 日期：2026-07-16
> 状态：待用户评审
> 产品定位：电诈询问结束后的单份笔录辅助复盘工作台
> 当前规则性质：项目工作规则，待客户提供正式“三现四流”模板后替换并验证

## 1. 设计结论

V1 不建设综合办案平台，集中完成一个可演示、可复核、可留痕的闭环：

```text
上传笔录
  -> 解析并保留原文位置
  -> 按指定规则集审查
  -> 民警定位证据并形成补问清单
  -> 对待处置项进行确认、加入补问清单或忽略
  -> 完成本次复核
  -> 回看记录并导出审查报告
```

V1 将机器结论和人工处置严格分开：机器结论形成后保持不变，民警无需录入实际问答，只需将每个待处置项分流为“确认问题”“加入补问清单”或“忽略”。三种分流都表示本次复核已经处理该项，实际补问不阻塞本次复核归档。

## 2. 用户与使用时机

### 2.1 核心用户

- 办案民警：完成一轮询问后，复核漏问和回答不完整事项，整理下一轮补问提纲。
- 审核人员：检查规则依据、原文证据和人工处置情况，确认本次复核是否完成。
- 规则管理员：后续维护客户确认的规则集、版本和生效范围；V1 只读展示，不开放编辑。

### 2.2 使用边界

- 系统只提供复盘提示，不作案件定性、法律结论、证据效力或责任判断。
- 当前仅使用虚构或脱敏材料。
- 客户模板到达前，页面必须显示“工作规则，非正式业务标准”。
- 模型仅在公司内网可访问属于部署环境约束；离线开发使用模拟响应和内置脱敏样例，不伪装成真实模型结论。

## 3. 民警反馈闭环

### 3.1 结果页默认视图

结果页默认展示“待处置”问题，而不是把已覆盖、遗漏、不完整、不适用等量铺开。顶部显示：

- 待处置数量。
- 已加入补问数量。
- 已解决数量。
- 无需处理数量。
- 当前复核是否可以完成。

页面继续使用左侧原文、右侧审查结果的双栏布局。点击问题定位并高亮原文，结果项再次点击可收起。

### 3.2 单条问题操作

对 `missing` 和 `incomplete` 结果提供以下操作：

1. **确认问题**：接受机器判断，保留在审查报告中，但不加入补问清单。
2. **加入补问清单**：接受机器判断，并将系统建议问题加入可集中复制的补问清单。
3. **忽略**：不加入补问清单，在审查报告中保留人工忽略记录；可选原因标签，不强制输入文字。
4. **复制补问内容**：复制单条或全部建议，便于民警在系统外整理问话提纲。

### 3.3 整单操作

- “查看补问清单”：集中展示已加入的建议问题，支持排序、编辑和复制全部。
- “完成本次复核”：只有全部 `missing` 和 `incomplete` 结果均已完成三选一分流时才可执行；完成后自动归档到审查记录。
- “重新打开复核”：对已完成任务追加重新打开事件，不删除原操作记录。
- “打印/导出报告”：输出机器审查和人工处置的完整摘要。

### 3.4 人工处置状态

机器规则状态保持：

```text
covered | missing | incomplete | not_applicable
```

人工处置状态调整为：

```text
pending        待复核
confirmed      已确认问题
supplemented   已加入补问清单
ignored        已忽略
```

`confirmed`、`supplemented` 和 `ignored` 都是本次复核的已处置终态。状态只表示当前汇总；后续需要完整审计时再增加追加式人工操作事件。

### 3.5 状态流转

```text
pending
  |-- 确认问题 ------> confirmed
  |-- 加入补问清单 --> supplemented
  `-- 忽略 ----------> ignored
```

## 4. 页面与导航

### 4.1 新建审查

- 上传 PDF/DOCX，展示格式、大小和脱敏提示。
- 显示模型连接状态、当前规则集名称和版本。
- 模型离线时仍可打开内置演示，但真实上传入口禁用并说明原因。

### 4.2 审查结果

- 保留原文定位、问题分组、缺失要素、判断说明、建议补问和规则来源。
- 默认筛选待处置项，已覆盖和不适用可折叠查看。
- 增加补问清单抽屉、处置表单、整单完成状态和报告入口。

### 4.3 审查记录

V1 将当前预留入口实现为真实页面：

- 显示文件名、创建时间、处理状态、待处置数量、复核状态、规则版本和模型名称。
- 支持按文件名、时间、处理状态搜索筛选。
- 点击记录重新进入结果页。
- 本地开发使用 SQLite 后，服务重启仍可回看记录。

### 4.4 规则管理

V1 只做规则集只读页面：

- 显示规则集名称、版本、状态、来源、适用场景和更新时间。
- 展开查看三现四流分类、触发条件、必查事实、证据要求和建议补问。
- 当前规则显著标记“工作规则，待客户确认”。
- 不提供新增、编辑、发布、回滚和审批操作。

## 5. 技术方案

### 5.1 前端

- 保持 React 18 + TypeScript + Vite。
- 保持 Lucide 图标和现有紧凑型政务工作台样式。
- 引入 TanStack Query 管理任务轮询、记录列表、规则集和人工操作等服务端状态，替代继续扩张的顶层 `useState`。
- 人工处置表单优先使用轻量受控表单；字段继续增长时再引入 React Hook Form，不在 V1 同时增加两套表单方案。
- 使用浏览器打印样式实现 V1 报告打印和“另存为 PDF”，不引入依赖系统组件的 PDF 渲染库。

### 5.2 后端

- 保持 FastAPI + Pydantic v2 + httpx。
- 保持解析、视觉识别、模型请求、结果校验四个模块边界。
- V1 使用 Python 标准库 `sqlite3` 持久化完整任务 JSON，不增加 ORM 依赖。
- SQLite 文件默认位于 `backend/data/reviews.db`，可通过环境变量调整。
- 正式建设阶段再根据部署规模评估 PostgreSQL 和 Repository 抽象，不在当前演示闭环中过早引入。

### 5.3 数据存储

```text
FastAPI route
  -> application service
      -> SQLite task store
          `-- review_tasks(id, updated_at, payload_json)
```

不选择 MongoDB。审查任务、规则版本、人工操作和审计事件之间存在明确关系，且后续需要筛选、统计和追溯，关系数据库更适合。

### 5.4 文件存储

- 数据库只保存文件元数据、哈希和存储引用，不把大文件二进制直接写入业务表。
- V1 默认不持久化原始上传文件，只保存标准化后的脱敏文本、页段索引和结果，降低数据风险。
- 正式环境若需保留原文件，使用受控文件服务或对象存储，并配置加密、访问权限、留存期限和删除策略。

## 6. 数据模型

### 6.1 `review_sessions`

- `id`
- `external_case_ref`：可选，预留办案系统案件标识。
- `title`：默认使用文件名生成。
- `review_status`：`open | completed | reopened`。
- `created_by`、`created_at`、`completed_at`。

一个会话后续可以包含初次笔录和补充笔录，V1 仍只创建单文档会话。

### 6.2 `documents`

- `id`、`session_id`。
- `original_name`、`format`、`size_bytes`、`sha256`、`page_count`。
- `parser_version`。
- `normalized_content`：JSON，保存页、段落、来源类型和识别置信度。
- `storage_key`：可选，正式文件服务引用。

### 6.3 `review_runs`

- `id`、`session_id`、`document_id`。
- `status`、`error_code`、`error_message`。
- `rule_set_id`、`rule_set_version`。
- `model_provider`、`model_name`、`model_strategy`。
- `started_at`、`completed_at`。

### 6.4 `review_results`

- `id`、`run_id`、`rule_id`、`rule_version`。
- `machine_status`、`fact_coverage`、`missing_facts`。
- `evidence_page`、`evidence_paragraph`、`evidence_text`。
- `reason`、`suggested_question`、`advisories`。
- `current_manual_status`：人工状态缓存，用于列表查询。

机器字段形成后不可由人工操作覆盖。

### 6.5 `manual_actions`

- `id`、`result_id`、`action_type`。
- `from_status`、`to_status`。
- `reason_code`、`note`。
- `question_text`、`answer_text`。
- `actor_id`、`created_at`。

每次操作新增一条记录。`review_results.current_manual_status` 只保存最新汇总状态。

### 6.6 `rule_sets` 与 `rules`

- 规则集：名称、版本、来源、状态、适用案由、生效时间和内容哈希。
- 规则：规则编号、三现四流分类、名称、适用范围、严重程度、触发条件、必查事实、证据策略和补问模板。
- 已用于审查的规则版本不可原地修改，只能创建新版本。

### 6.7 `audit_events`

- 记录任务创建、审查完成、人工处置、整单完成、重新打开和报告导出。
- 只记录用户、动作、对象、时间和非敏感摘要，不记录身份证号、手机号、银行卡号等完整原文。

## 7. 规则模板

“三现四流”是七个分类，不应永久限制为只有七条检查结果。客户模板到达后，一个分类下可以拆成多条原子检查规则。

### 7.1 规则层次

规则集按业务方模板选择性包含四层，未获业务确认的层次不得启用：

1. **笔录基础完整性**：询问时间、地点、人员、权利义务告知、签名等结构项，优先使用确定性解析或人工确认。
2. **三现四流事实完整性**：案发现场、涉案现物、电子现痕及人员流、信息流、资金流、行为流，是电诈复盘主清单。
3. **条件场景规则**：出现 APP、逐笔转账、寄递、返利提现或第三方人员等事实后才触发。
4. **交叉一致性提示**：检查时间线、金额、账户、人员称谓前后矛盾；业务方确认前只作为风险提示，不计入硬缺失。

每条规则只检查一个可解释问题，避免一个规则同时包含过多事实，导致民警无法判断应补问哪一项。

```json
{
  "ruleSet": {
    "id": "telecom-fraud-three-present-four-flows",
    "name": "电诈三现四流笔录审查规则",
    "version": "0.1-working",
    "status": "working",
    "source": "项目工作口径，待客户确认",
    "caseTypes": ["电信网络诈骗"]
  },
  "rules": [
    {
      "id": "FLOW-FUND-001",
      "category": "四流",
      "dimension": "资金流",
      "name": "逐笔转账要素完整性",
      "scope": "conditional",
      "severity": "important",
      "appliesWhen": {
        "anyKeywords": ["转账", "支付", "充值"]
      },
      "requiredFacts": [
        {"key": "transfer_time", "label": "转账时间"},
        {"key": "amount", "label": "转账金额"},
        {"key": "counterparty", "label": "对方账户"},
        {"key": "transaction_id", "label": "交易流水号"}
      ],
      "evidencePolicy": "定位能够支持该笔转账要素判断的原始问答",
      "suggestedQuestions": [
        "请说明该笔转账的时间、金额、收款账户和交易流水号。"
      ],
      "referenceHints": []
    }
  ]
}
```

规则模板导入流程：

```text
客户 Word/Excel/PDF 模板
  -> 人工确认栏目含义
  -> 转换为版本化规则 JSON
  -> JSON Schema 校验
  -> 生成脱敏正反例
  -> 业务方确认预期结果
  -> 发布为 working/approved 版本
```

禁止直接让模型读取客户模板后自行决定正式规则。模板必须先经过人工结构化和业务确认。

## 8. 模型输出与规则扩展

继续优先使用 Qwen Strict JSON Schema，但移除 Pydantic 模型中写死的七个字段。后端根据当前规则集动态生成：

- 顶层固定规则 ID 键。
- 每条规则固定 `requiredFacts` 键。
- 每个事实只能为 `covered | missing | unknown`。
- 模型选择证据页码和段落，不输出最终证据原文。

本地使用 `RootModel` 或 TypeAdapter 解析动态字典，再由确定性代码检查规则 ID 集合、事实键、证据位置和状态一致性。这样客户新增或拆分规则时，只更新规则集，不修改固定 Pydantic 字段。

当规则数量超过单次上下文的稳定范围时，按三现四流分类并行审查，最终由程序合并；V1 的规则数量较少时继续单次调用，避免过早复杂化。

## 9. 报告模板

V1 报告采用打印友好的 HTML 模板，包含：

1. 文件信息、审查时间、归档时间、规则集版本和审查模式。
2. 已覆盖、遗漏、不完整、不适用和待处置数量。
3. 每条问题的规则、缺失要素、原文证据和补问建议。
4. 每项人工分流结果，以及进入补问清单的建议问题。
5. 整单复核状态及“智能审查结果仅供复盘参考”说明。

V1 使用浏览器打印或另存为 PDF。客户提供正式报告模板后，再使用 `docxtpl` 或 `python-docx` 生成 DOCX，不在没有模板时提前固定正式文书版式。

## 10. API 调整

- `GET /api/v1/reviews`：审查记录列表和筛选。
- `GET /api/v1/reviews/{id}`：现有详情接口保留。
- `POST /api/v1/reviews/{id}/complete`：完成整单复核。
- `POST /api/v1/reviews/{id}/reopen`：重新打开。
- `GET /api/v1/reviews/{id}/follow-ups`：补问清单。
- `POST /api/v1/reviews/{id}/results/{rule_id}/actions`：追加人工操作。
- `GET /api/v1/reviews/{id}/report-data`：返回固定结构的报告 JSON 数据。
- `GET /api/v1/rule-sets`：规则集列表。
- `GET /api/v1/rule-sets/{id}/versions/{version}`：规则集只读详情。

前端使用 `/reviews/{id}/report` 路由渲染打印页面，并消费 `report-data`。V1 不提供后端 PDF 文件生成接口。保留现有人工决定 PATCH 接口一段迁移期，前端切换后再移除。

## 11. 错误与并发处理

- SQLite 单次任务保存使用事务，人工分流和整单状态同步保存。
- 已完成复核的任务默认禁止继续修改，必须先重新打开。
- 模型调用失败不生成部分审查结论；人工操作失败不影响已经形成的机器结果。
- 报告生成失败只提示重新生成，不改变复核状态。

## 12. 安全与部署

- 公司内网模型恢复后执行真实连通和结构化输出验证。
- 正式环境上线前确认模型、数据库和文件存储均处于批准环境。
- API Key 只通过环境变量或密钥服务注入。
- 数据库连接、文件存储和传输使用加密。
- 后续接入统一身份认证，所有任务按单位和用户授权隔离。
- 配置数据留存、删除和脱敏策略后，才允许处理真实案件材料。

### 13.2 规则黄金样例

`verify:model` 从“返回七条结果”升级为语义验证：

客户模板到达前使用工作规则样例，结果只用于技术调试；模板确认后重新建立业务验收基线。

## 14. 阶段实施顺序

### 阶段 A：不依赖内网模型

1. 将内存任务字典替换为 SQLite 任务存储。
2. 固定无输入的三选一人工分流状态。
3. 实现补问清单、整单完成和重新打开。
4. 实现审查记录页面与记录回看。
5. 实现规则集只读页面和工作规则版本标识。
6. 实现打印报告。
7. 使用模拟模型响应完成自动化和浏览器测试。

### 阶段 B：回到公司内网

1. 运行模型健康检查和完整 `verify:model`。
2. 使用三份脱敏样例进行真实模型测试。
3. 检查耗时、重试、Schema 兼容性和证据定位。
4. 客户模板到达后完成规则结构化、版本发布和黄金样例标注。
5. 根据误报、漏报和证据错误调整规则描述与提示词。

## 15. 一期汇报完成标准

- 单命令启动，离线演示和内网真实模型边界明确。
- PDF/DOCX 可完成解析、审查、证据定位和错误提示。
- 待处置问题可以确认、加入补问清单或忽略，无需输入实际问答。
- 全部问题处置后可以完成整单复核。
- 审查记录可回看，服务重启后仍保留脱敏演示记录。
- 可打印一份包含机器结论和人工处置的审查报告。
- 页面展示规则集版本、模型版本和工作规则性质。
- 三份脱敏样例能够稳定覆盖基本完整、明确漏问和复杂场景。
- 回到内网后真实模型验证通过；客户规则未到时不宣称业务规则验收完成。

```text
  -> 对另一条选择无需处理并填写原因

  -> 在审查记录中重新打开
  -> 打印审查报告
  -> 展示规则集只读页并说明客户模板接入方式
```
